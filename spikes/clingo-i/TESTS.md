# clingo-i — tests

This note is for a reader who wants to know what clingo-i's own tests check, and why each one is there. Each item names the risk it guards and what would get through without it. The program is described in `DESIGN.md`, beside this file, which also defines its terms and relations.

The tests cover what the corpus cannot see. `uv run pytest` in this directory runs them at the PR bounds, `uv run pytest -m slow` at the slow bounds, and `uv run pytest --backend=clingo-i` from the repository root runs the corpus through the program. They run in parallel on every core (pytest-xdist, `-n auto --dist loadgroup` in `pyproject.toml`); `-n 0` runs them in one process. L9 cannot see a driver bug, so the driver is tested on its own (`correctness-strategy.md` §4.1).

## The program

`test_interpret.py`, on inline Turtle and a small inline module set, not the repo's profiles.

- **Integrity.** A rule deleted from the program must not leave a verdict standing on the missing part. Deleting one rule from `kleene.lp`, `applies.lp`, `completion.lp`, or `resolve.lp` (`DELETIONS`), or the `eq` rule of `compare.lp` or the unresolved-read rule of `operand.lp` (`CONSTRAINT_DELETIONS`), turns the reply into an error where the intact program answers. So does an atom with two effects. Each deletion's vector gets a definite verdict from the intact program: the constraint vector puts a `t` member, which the deletion does not touch, under an `or`.
- **Explanation.** Each basis role and elimination rule on a small policy, so a wrong row cannot hide behind a right verdict: a `u` candidate removed by a `t` prohibition under `prohibit`; a `u` prohibition beside a `t` candidate under `prohibit`, which removes nothing; an irrelevant `u` atom, not named `unknown`; each range; the combination rule, on facts. Two rules on one absent target, and two on one absent assignee, are completed separately (`test_absent_fields_are_not_shared`): one shared variable would give `NotApplicable` to `Permit` under `perm`, where separate ones give `Deny` to `Permit`.
- **Worked examples** (`test_worked_example`, `test_constraint_worked_example`). The replies of `DESIGN.md` § Worked example, unknown parts included, and of the worked example in `compare.lp`, so neither text can drift from the program.
- **Operators** (`test_operators`, `test_hierarchy_operators`). Each operator on a value that makes it `t` and one that makes it `f`, so a rule that answers one way regardless is caught. Each misfit on a value that a two-valued reading would make `f`: an IRI against a string, two language tags, an instant against a number. `isA` reads an `rdf:type` edge from the SOTW closure, so a closure the driver dropped would show. An empty read set is vacuously part of anything.
- **Concepts** (`test_concept_operators`, `test_concept_broader_cycle`). One scheme whose memberships use all three forms and whose edges include a `skos:narrower` triple. `eq` holds on identity, one inverted edge, and two edges, and not upward or with no path; without the scheme, the same edges are not read. `neq` and `isNoneOf` exclude a concept below the right value. A read concept in no scheme, and a string, are `u` under `eq` and `neq` alike. The SOTW supplies a read concept's edge and membership, and an edge alone leaves it `invalid`; a right operand in a scheme by the SOTW only is rejected. A cycle of `broader` edges terminates. Deleting the narrower inversion, the transitive step, the `hasTopConcept` membership, the read membership, or the out-of-scheme rule fails at least three rows each. The three rejections are rows of `test_constraint_rejections`.
- **Reads** (`test_state_read`, `test_reads`). Every SOTW status but `resolved`, and no fact at all, is `u`, never `f`; so are two values or none for a `one` operand, and a read value outside the range. The context reads the assignee and the clock.
- **Several sources** (`test_several_sources`, `test_several_sources_set`). Answers from two sources, combined as `due2-workflows.md` §3.3, *Several sources*, states: agreement is `resolved`, disagreement and a source's own `conflict` are `conflict`, a value outweighs `unresolved` and `invalid`, and among answers without values `unresolved` outweighs `invalid`, which outweighs `missing`. A resolved answer with no members, for a set-valued operand, has values: it differs from one with a member and agrees with another empty one. Without the guards that order the statuses, the invalid-and-unresolved row has no reply output; a combination that counts a resolved answer as having values only when it lists one fails both set rows.
- **Several policies** (`test_multiple_policies`). A second policy in its own text of `policies`, describing its own rule, is admitted (each text is normalised alone, and a text that names a rule only the other text describes is not admissible alone), and the same policy added to the first text is `MultiplePolicies`. A rule that allowed one policy in all, rather than one per text, rejects the first.
- **A profile stays with its policy** (`test_profile_stays_with_its_policy`, `test_profile_reaches_its_own_policy`, `test_shared_leaf_binds_alike`; #149). W1 normalises each policy alone (`due2-workflows.md` §4), so a second text, policy `ex:q`, that names a profile must not change the reply for the first, policy `ex:p`, which names none. Each row gives `ex:p`'s reply alone, and again beside `ex:q`'s text, in both orders. `ex:q`'s profile would give `ex:p` a conflict default, bind its unbound operand, own its operand's unit, or put its right operand in a scheme. A driver that merged the texts' layers fails every row. The controls show that a profile still reaches the policy that names it, so a fix that dropped profiles from a corpus is caught. A leaf that two texts share binds alike or is `IdentityConflict`: without the comparison in `_combine`, two texts that bind the leaf's operand to different properties are both admitted, and the leaf reads whichever binding the corpus kept.
- **Bindings** (`test_binding_layers`, `test_profile_module_spans_files`, `test_retyped_operand`, `test_operand_range_mismatch`). The highest layer that states the property gives it: with a profile binding, a request giving only the core property is `u`, not a match. Two profile modules that agree bind, and two that differ are rejected, so a rule that let one module win is caught. A profile split over two files is one module, so a rule that compared files is caught. A policy may restate where a baseline operand reads, or its type with the owner's values, and any other type is rejected; the `due2:set` row fails if the default does not count as stated. A range of another kind than the read property's is rejected, and `rdfs:Literal` matches any literal range but not a class range.
- **Hierarchies** (`test_typed_part_of`). A requested asset in a target collection matches, and a non-member does not; a named party in an assignee collection matches; an untyped collection and a cross-kind edge decline.
- **Rules and refinements** (`test_prohibition_constraint`, `test_refinement`). A constraint on a prohibition decides a `Deny`; a refinement is a conjunct of the atom.
- **Units** (`test_units`, `test_completion_key_units`; `decisions/0049`). A constraint in its binding's `due2:unit`, or in none, compares the values; one in another unit is rejected with `OperatorTypeMismatch`; one with a unit on a binding that declares none is `u` with status `misfit`, whether the read value would match or not. Without the unchecked rows, a reading that treats the unit as a label passes; without the differing row, a check that ignores a unit passes; without the first rows, one that blanks every unit passes. In the completion key, the constraint's own unit is a component, so two leaves with the binding's unit share a variable and a leaf without one does not; two leaves with an unchecked unit are opaque and never paired, so the verdict is `Indeterminate`, not the `Permit` a pairing would claim.
- **The completion key** (`test_completion_key`, `test_binding_not_operand_iri`). Two rules under `perm`, each with one `u` leaf on an unresolved operand. When the leaves share every component of the key and one is the other's complement, one rule applies in every completion, and the verdict is `Permit`. Each other row changes one component (the property, the right operand, the operator, `5` against `5.0`, the right operand set, or the scope), which gives two variables and `Indeterminate`. Without the shared rows, one variable per leaf would pass; without the differing rows, a key that merged too much would. Two operand IRIs bound to one property share a variable, so a key on the operand IRI is caught.
- **Opaque parts** (`test_opaque_is_not_paired`). `decisions/0016`'s example: permissions `x lt 5` and `x gteq 5`. With `x = 3`, `Permit` and no unknown part. With `x` absent, `"abc"`, or `ex:v`, the leaves are opaque, and the reply is `Indeterminate`, `NotApplicable` to `Permit`, naming the status. With `x` unresolved, one variable gives a definite `Permit`. A program that paired every `u` leaf would give `Permit` in all four rows.
- **Unknown parts** (`test_unknown_parts`, `test_invalid_read_is_reported`). One leaf on a state property under every status the SOTW can give: `missing`, `invalid`, `conflict`, `unresolved`, no fact, and `resolved` with no value, two values, or a misfit value. An absent target and an absent assignee are `missing`. An `f` atom (its action does not match) reports nothing, though its leaf is unresolved and its assignee absent. A read value outside the declared range is `invalid`. A status mapped to the wrong name, or a part reported for an `f` atom, fails a row.
- **Live leaves** (`test_leaf_in_f_disjuncts_only_is_not_reported`). Under `or(dead, z)`, with `z` unresolved, `dead` is one of five trees in which a `u` leaf `y` lies only in `f` disjuncts: under an `f` conjunct, under `dprod:not` of a `t` disjunction, under a double negation, in an `xone` with two `t` members, and in a negated `xone`. Only `z` is named. Two controls, `and(lt, y)` and a negated `xone` of `lt` and `y`, with `lt` a `t` leaf, name `y` as well. Named by tree membership, all five would name `y`; without the flip at `dprod:not`, the second and fifth would.
- **A decided leaf** (`test_decided_leaf_is_reported`). A permission `x eq ex:v or y eq ex:w`, with `x` resolved to `ex:v` and `y` unresolved, is `Permit`, and names `y` as `unresolved`. A program that reported only `u` atoms would name nothing.
- **The completed basis** (`test_completed_basis`). The two shapes of `resolve.lp`, *The cautious basis* (a `Permit` whose basis names a `u` permission, and a `Deny` with an empty basis) and the `Permit` with an empty basis of the worked example in `completion.lp`. They pin the basis that `decisions/0016` #4 settled.
- **The cap** (`test_variable_cap`). An `or` of `n` leaves on one unresolved operand, each with its own right operand and each written twice: `n` variables. `n = 64` answers and `n = 65` declines as `variable-cap`. The repeated leaves leave ground `var/1` atoms that no model makes true, so a count of the ground atoms would decline both.
- **Rejections and declines** (`test_constraint_rejections`, `test_constraint_declines`, `test_datatypes_differ_without_a_range`, `test_derived_strings_decline`, `test_node_in_two_scopes`). Each code and reason of `DESIGN.md` § Declines and § Errors that a constraint or a binding produces, on a minimal policy, so a check that is deleted or never fires is caught.
- **Declines.** A feature the spike does not read must decline, never be ignored, and one it reads must not decline. `sotw.evidence` (with an issuer) and `sotw.activation` give a `Permit` on a policy without duties (`test_duty_inputs_are_read`). A policy with both `odrl:inheritFrom` and `odrl:remedy` declines naming `odrl:inheritFrom`, the smaller IRI, with the same reason on a repeat. An unknown predicate on a rule declines; an allowlisted annotation does not; an unknown predicate on an asset node outside the vocabulary namespaces is ignored. Each input-side decline names its field, and an unplaceable input value names its reason.
- **Protocol.** `main.py` answers `init` with `ready`, declaring `interpret`, and echoes the request `id`.

## Duties

`test_duty.py`. The first group runs solve 1's program, whose relations show what a reply would hide behind a decline or a verdict:

- **Inheritance.** The duty of a permission with two assignees is two duty atoms, each the precondition of the parent atom with its bearer. Shared by two permissions with one assignee, it is one atom, and a parent with no assignee passes `none`. A program that dropped the bearer from the id, or gave each parent atom every duty atom, fails a row. A duty that names its own party keeps it under every parent atom. A root obligation takes the policy's target and parties, and a precondition duty takes neither.
- **Bearers.** A root obligation with `dprod:subjectOfDuty` and a different policy-level `odrl:assignee` has the stated party as its only bearer; without `states_bearer/1`, it would decline as `duty: bearer from two functions`, as the three DPROD contract cases did. A duty that states both functions with different parties declines, and with the same party does not.
- **The split.** An `and` of a state leaf, a witness leaf, and an `actionTime` leaf gives one guard and two witness conditions. A witness refinement of a duty's action is a witness condition. An `or`, an `xone`, or a `dprod:not` over a guard leaf and a witness leaf is `MixedDutyConstraint`, and an `or` of witness leaves alone is not. Without the conjunction rule, the first row's `and` is one part with both kinds of leaf, and is rejected.
- **Relations and timing.** A stated `odrl:output` is the relation, and the policy's target is not taken. Each deadline kind, and each instance scope with `member` the default; an unknown scope declines.
- **Rejections.** `InvalidTiming` (two deadlines, and a deadline of another type), `TimingOutsideDuty`, `TargetAndOutput`, `MissingAction`, `RuleReferenceCycle`, and `WitnessOutsideDuty` for a witness refinement of a permission's action; without the action branch of `node_tree/2`, the last passes.
- **Recurrence.** A `dprod:recurrence` declines the vector as `recurrence`.

The second group runs one model of solve 2's program, integrity constraints included, so a finding or check that a rule forgets has no value and fails the solve:

- **Owed** (`test_unguarded_duty_without_evidence_is_outstanding`, `test_guard_decides_owed`). A duty with no guard is owed and, with no evidence, `outstanding`; without the identity 2 in `owed`'s `#min`, it would have no `owed` value. A guard on a missing fact makes `owed` `u`, and the duty still has an instance; only an `f` guard removes it.
- **The witness test** (`test_matching_evidence_fulfils`, `test_each_failing_check_fails_the_witness`, `test_attested_issuer_and_discharged_reference_pass`, `test_no_named_subject_leaves_the_actor_unknown`). Matching evidence fulfils the duty. Each of six checks (the actor, the action, `effective`, the attester, the discharge, the object) then fails on its own and makes the witness `f`; a check that answered `t` regardless would leave the duty `fulfilled`. The attester check fails on evidence with no issuer and on an issuer that is neither the duty's `due2:attestingParty` nor below it. An issuer that is the attester, or a member of it under the party closure, passes, and so does a discharge under the request's reference; without the closure rule of `attested/2`, the member's evidence would not count. A request that names no subject makes the actor check `u` and the duty `unknown`, where a two-valued reading would say `outstanding`.
- **The witness worlds** (`test_witness_condition_is_read_from_the_evidence`, `test_witness_only_nodes_are_not_world_k_items`, `test_action_time_is_the_evidence_time`). A witness leaf reads the evidence's params in `wit(E)`: matching, `t`; different, `f`; absent, `u`, and the duty `unknown`. Read in world `k`, it would be `u` for every piece of evidence. In an `and` of a guard and a witness leaf, only the guard is a world-`k` item, and only the witness leaf is evaluated in `wit(E)`; without `witness_only/1`, world `k` would give the witness leaf the value `u`, with no evidence to read. `due2:actionTime` `lteq` 10 May is `t` for evidence of 1 May and `f` for 20 May; read from the request's 1 June, both would be `f`.
- **Live witness leaves** (`test_witness_parts_name_only_live_leaves`). Under `or(and(w1, w2), w3)`, with `w1` `f` and the others missing, only `w3` is named. Under `and(w1, w2)`, with one piece of evidence whose actor check is `f` and which lacks `w1`, and another that lacks `w2`, only `w2` is named. Named by tree membership, either would name a leaf that decides nothing.
- **Deadlines** (`test_deadline_decides_outstanding_or_violated`, `test_late_witness_is_not_timely`). An absolute deadline before `effective_at` makes an unfulfilled obligation `violated`, and one after it `outstanding`. A relative one counts from the activation, or from `effective_at` without one, so `P1D` is `violated` from an activation in May and `outstanding` without one. Evidence after the deadline is no witness; without the deadline check, it would fulfil the duty. This is the worked example in `duty.lp`.
- **In force** (`test_obligation_without_a_matching_rule_is_not_in_force`). A root obligation in a policy with no permission or prohibition is not in force, and has no instance, although the request asks for the obligation's own action on its target. A program that matched the obligation itself would find it in force.
- **A collection bearer** (`test_each_member_bears_a_collection_duty`, `decisions/0018`). With `ex:alice` and `ex:bob` members of the bearer `ex:coll`, and `ex:alice` the subject, her act is a witness and `ex:bob`'s is not. With `ex:coll` the subject, its own act is. With no subject, a member's act is `u` and a non-member's `f`. Read as equality with the bearer, `ex:alice`'s act would be `f`, as in the corpus case `force-21`; read as membership, `ex:bob`'s would discharge her duty.

The third group checks W3 on replies:

- **Routes** (`test_outstanding_precondition_is_pending`, `test_fulfilled_precondition_permits`). An outstanding precondition gives `Pending`, with the duty as the route and in role `duty`; fulfilled, it gives `Permit`. Without `outstanding/3`, the first would be `Permit`.
- **Closure** (`test_violated_precondition_closes_the_route`). A precondition owed and violated gives `NotApplicable`, an `eliminated` row with rule `violated_precondition`, and the permission in role `closed`. Without `closed/2`, `Pending` would offer a route that can no longer be taken.
- **The frontier** (`test_frontier_keeps_the_least_duty_sets`, `test_ready_route_beats_a_pending_one`). Of two routes, one whose duties strictly contain the other's is dropped, two incomparable ones are both listed, and two with one duty set are one alternative. Without `dominated/2`, the first would list both; without the collapse, the last would list one set twice. A route with no outstanding duty gives `Permit` and no frontier.
- **An uncertain route** (`test_pending_basis_under_an_uncertain_route`). The `Pending` exception of `resolve.lp`, *The cautious basis*: frontier `[[ex:d, ex:d2]]`, basis `ex:d` only, and the missing parameter as the unknown part. Read from the completions instead, the frontier would depend on the variable.
- **A route beyond the listed frontier** (`test_pending_basis_beyond_the_listed_frontier`). The second `Pending` example of `resolve.lp`, *The cautious basis*: permissions on `ex:x eq 5` and `ex:x neq 5` share a duty, so the basis names `ex:d3`, which the frontier `[[ex:d]]` does not. A basis read from the listed frontier, or a check that the basis's duties are a subset of the frontier's, would fail it.
- **`u` duty findings** (`test_unknown_owed_is_completed`, `test_guard_and_rule_leaf_share_a_variable`, `test_unknown_fulfilled_is_its_own_variable`, `test_unknown_in_force_is_reported_and_completed`, `test_missing_target_leaves_rule_and_obligation_unknown`).
  - A guard on a missing fact leaves `owed` `u`: the reply is `Indeterminate`, `Pending` to `Permit`, names the duty `unknown`, and reports the guard's operand `missing`. Uncompleted, a `u` `owed` would leave the verdict undefined in every world.
  - A guard leaf with a rule leaf's key reads its variable, so the range is `NotApplicable` to `Pending`, where independent variables would reach `Permit`.
  - A `u` `fulfilled`, from no subject or from a missing witness parameter, gives `Pending` to `Permit` and reports the assignee or the parameter under the duty. Without the actor row of `unknown_part/3`, the first would name the duty `unknown` with no reason.
  - A guarded obligation with its guard `u` is listed `unknown` and reports the guard. An obligation never moves the verdict (`decisions/0045`), so the verdict is `Permit` and the obligation is not named `unknown`. Without the completion of `in_force`, the one value per world that `integrity.lp` asks of every completed finding would fail the solve.
  - An absent target leaves the permission and the obligation `u`, each with its own variable, and reports the target under both.
- **Evidence without `effective_at`** (`test_evidence_without_effective_at_declines`). The decline of `duty.lp`, *Fulfilled and status*. Without it, the duty would be `unknown` with no unknown part to say why.
- **A violated obligation** (`test_violated_obligation_is_reported_and_never_denies`). An obligation in force whose deadline passed unwitnessed is listed `violated`, in role `obligation`, under `Permit`: an obligation never denies (`decisions/0045`). With an obligation rule in `deny/1`, the verdict would be `Deny`.

## The brute-force differentials

`test_brute_force.py`, with Hypothesis (`correctness-strategy.md` §4.1). Each differential runs as four copies, each with its own random seed (`COPIES`), so that parallel workers share it; draw counts are per copy.

- **The oracle** (`test_matches_brute_force`). It generates policies of permissions and prohibitions under each conflict strategy, with absent targets and unnamed assignees. A rule may carry a constraint tree of depth two over the operands `ex:o0` to `ex:o2`, each read from the request or the state, with `eq`, `neq`, and the order operators against `1`, under `and`, `or`, `xone`, and `dprod:not`, with members as a list or as repeated values, and no two leaf members of an `xone` the same (`decisions/0022`). In a quarter of the cases, one rule's first constraint `t` becomes `or(dead, t)`, where `dead` is `f` whatever its subtree `sub`: `and(F, sub)`, `dprod:not(or(T, sub))`, or `xone(T, T2, sub)`, with `F`, `T`, and `T2` leaves on an operand that has a value, `F` one that is `f`, and `T` and `T2` two different ones that are `t`. Every leaf of `sub` lies only in `f` disjuncts. An absent request parameter is `missing`, and a state property with no fact is `unresolved`.

  A Python oracle enumerates the completions, flips each variable alone, and derives the verdict, the basis, the eliminations, the `unknown` atoms, the range, and the unknown parts, which must equal the reply. It values a tree by supervaluation: it tries `t` and `f` for each `u` leaf occurrence on its own, and the tree is `u` when the tries disagree. That is strong Kleene logic for independent leaves, computed without the program's ranks. Under a completion, each unresolved leaf takes its variable's value, negated for a complement operator, and a missing leaf stays `u`. An atom whose parts are still `u` (an absent target or party included) takes its own variable, as `fin(I)` does. An unresolved leaf's variable is its operand and positive operator, so `neq` reads `eq`'s variable negated, `gteq` reads `lt`'s, and `gt` reads `lteq`'s; every generated leaf is in rule scope against `1` with no unit, so these are the only key components that vary. The basis is the rows that hold in every completion (`resolve.lp`, *The cautious basis*). The unknown parts are, for every rule whose finding is not `f`, every absent field and every leaf without a value that lies in a disjunct of the rule's DNF that is not `f`. The oracle builds that DNF by De Morgan and distribution, with `xone` as the disjunction of its terms (`due2-profiles.md` §5), and does not simplify it: `a ∧ ¬a` stays, since under Kleene logic it is `u` when `a` is. It shares no code and no reading with `live/4`, which walks the tree instead. The oracle reads the generated rules, not the driver's facts, and shares with the program only the spec's variable key (`due2-workflows.md` §6.4) and the statuses of `decisions/0016`. Each copy makes 400 draws after twenty-two explicit cases.
- **The explicit cases** fix shapes random draws rarely reach:
  - a `u` atom whose variable changes no verdict, under `prohibit` and `invalid`;
  - two atoms on one absent target, each with a variable of its own;
  - one tree per connective that changes value if the connective is misread (`and` as `or`, `or` as `and`, `dprod:not` as the identity, `xone` as `or`);
  - a `u` leaf under an `and` and an `or` that decide anyway, and a lone `u` leaf;
  - an `or` of a leaf and its complement, which is `u` under Kleene logic but `t` in every completion when unresolved, and stays `u` when missing;
  - two rules whose leaves are complements (`lt` and `gteq`), so one of them applies in every completion when unresolved, and neither need when missing;
  - a tree with a missing and an unresolved leaf, where the world leaves it `u` and the atom's own variable decides;
  - an `f` atom with an absent target and a missing leaf, whose unknown parts are not reported;
  - a `u` leaf under a `t` node, beside an open leaf with the same variable, where only the open leaf is read;
  - four rules `or(dead, u)`, with `dead` each of `and(F, u)`, `dprod:not(or(T, u))`, `xone(T, T2, u)`, and `dprod:not(xone(T, and(F, u)))`.
- **Duties** (`test_duties_match_brute_force`). A second oracle adds duties (`due2-workflows.md` §5.3, §6, `decisions/0018`, `decisions/0019`). Each permission may require some of three duties, and the policy may carry a root obligation, which is reported and never moves the verdict (`decisions/0045`). A duty may have a guard tree, a passed deadline, and one piece of evidence whose actor is `ex:alice` or `ex:bob`, under a request whose subject is `ex:alice` or absent. The oracle completes a guard as a rule's tree, so a guard leaf with a rule leaf's key reads its variable, and gives each other `u` finding, and each `u` `fulfilled`, a variable of its own. It derives the closed routes, the candidates, the listed frontier, the verdict, its range, the basis, the obligations, and the duties named `unknown`, and they must equal the reply. Each copy makes 300 draws after eight explicit cases: a violated precondition whose `owed` is `u`, which leaves its permission out of the listed frontier; two incomparable alternatives; a guard and a rule leaf on one variable; an absent target beside a violated obligation; no subject; two `u` `fulfilled` of which one is pivotal; the `Permit` with an empty basis of `resolve.lp`, *The cautious basis*; and one duty under two permissions with one bearer.
- **Killing the mutants** (`test_differential_kills_mutant`, `test_duty_differential_kills_mutant`). The rule differential must fail against each of the 17 rule mutants of § Mutants, and the duty differential against each of the 5 duty mutants, running the explicit cases and then 100 draws. The explicit cases alone kill the five duty mutants. This shows that each differential can see each mutant, not that its generator reaches it, since the explicit cases come first; the spaces show the reaching.
- **Generator strength** (`tests/measure_mutants.py`, a script, not a test). `uv run python -m tests.measure_mutants N` runs each mutant against generated draws alone, with no explicit cases and no shrinking, and prints the first exposing draw under seeds 0 to N − 1. It measures the generators; no test asserts its numbers, because the spaces' exposure is asserted instead.
- **An unknown read as false** (`test_opaque_leaf_as_f_fails_open`). The shrunk case that `uv run python -m tests.measure_mutants --shrink opaque-leaf-as-f` finds: a prohibition whose target and constraint parameter are both missing. The oracle replies `Indeterminate`, `Deny` to `NotApplicable`; the mutant replies `NotApplicable` with an empty basis and the same unknown parts. It pins the worked example of `docs/briefings/due2-briefing-2026-10-21.md`, Appendix C.3.
- **Shapes** (`test_generator_reaches_each_shape`, `test_duty_generator_reaches_each_shape`). Over 400 and 1,000 derandomized draws, each generator must reach every shape its differential relies on. For rules: every conflict strategy, an `Indeterminate` with a non-pivotal `u` atom, two `u` atoms sharing a variable, an atom with a variable of its own, an open tree with an opaque and a paired leaf, an `f` atom on an absent target, open leaves reading one variable with both polarities, two constraint roots that are the same leaf (which the key must merge), a `u` leaf under a deciding connective, and a `u` leaf that only `f` atoms read. For duties: a `u` `owed`, `fulfilled`, and `in_force`, a duty finding sharing a variable with a rule, `Pending`, two listed alternatives, a closed route, and an `Indeterminate` naming a duty. A generator change that stopped producing one would leave the differential passing on nothing; the test fails on a zero count instead.
- **Enumeration** (`test_enumeration_matches_fixed_solves`). The differential trusts that solve 2's answer sets are exactly the completions, and an oracle with the same mistake would hide a choice rule that admits a non-completion or misses one. Over four copies of 150 cases with at most six variables, the test solves solve 2's program once per assignment, each variable's value a fact and the choice rule deleted. Each fixed solve has one model; the enumeration has `2^n`, and their shown atoms are those of the fixed solves. The reply is `Indeterminate` exactly when the fixed solves reach more than one verdict. clingo's cautious consequences are the intersection of the fixed solves, so a misreading of the cautious enumeration is caught too.

## The bounded-exhaustive spaces

`test_spaces.py`, `tests/spaces.py`, `tests/space/` (`correctness-strategy.md` §1.1). A generator rarely produces some shapes, so a defect that shows only on them rarely fails a differential. The spaces check every input up to a bound against the same two oracles.

- **What a space is.** An ASP program in `tests/space/`, one answer set per input. Choice rules pick the rules and their constraint trees, the operand statuses, and the conflict strategy; in a duty space, also the duties, the edges by which permissions require them, the root obligation, and the request's subject. An *operand status* says how an operand is given: `value` (by the request), `resolved` (by the state), `missing` (by neither, so opaque), or `unresolved` (the state has no fact, so paired; `DESIGN.md` § Vocabulary). `trees.lp` is the catalog of constraint trees up to a size, included by `rules.lp`, `xone.lp`, and `duties.lp`; `candidates.lp` has no constraints. `tests/spaces.py` grounds a program, maps each answer set to a `Case` or `Duties` of `test_brute_force.py`, and orders the inputs smallest first: by the number of rules, then the total size of their trees, or, for a duty input, the number of edges. A failure is therefore reported on a smallest input that shows it. The expected answers come from the oracles only: a space program chooses what is checked, never what is right (`correctness-strategy.md` §5, ASP-generated).
- **Symmetry.** Inputs that differ only by an order the policy does not have, or by a renaming the oracle treats alike, give the same reply, so each space keeps at least one input of each class:
  - the rules are a multiset, kept sorted, because a policy's rules have no order;
  - the members of an `and`, `or`, or `xone` are sorted, because `render` in `test_brute_force.py` writes them as repeated objects of one RDF predicate, which have no order either;
  - the members of an `xone` are all different: two equal leaf members are malformed (`decisions/0022`), and two equal compound members, which are admitted, are left out to keep the catalog small, so no space checks them;
  - the operand statuses are sorted by operand: renaming the operands maps the catalog of trees onto itself, so some renaming of any input, with its rules and members re-sorted, sorts its statuses; the `pinned` and `xone` spaces fix the statuses instead;
  - with rules of one kind only, no conflict arises, so the strategy is `perm` unless the input holds both kinds;
  - in `candidates.lp`, the request's target is `a` or absent and its assignee `ex:alice` or absent, because `b` and `ex:bob` are the same renamed;
  - in `duties.lp`, the duties are sorted, because the three duty actions are interchangeable, and each is required by some permission, because a duty nothing requires decides nothing.

  Some classes keep more than one input (two equal rules still take their edges in either order), so the spaces are slightly larger than they need be, never smaller.
- **The counts** (`test_space_has_its_count`). A symmetry constraint that removes too much shrinks a space silently, since every remaining input still passes. `count` in `tests/spaces.py` computes each space's size in Python, without clingo: the trees of each size by dynamic programming over multisets of smaller trees, the multisets of `k` rules from `n` kinds as C(n + k − 1, k), three strategies for a set with both kinds, and, for duties, the multisets of duties times a nonempty set of permission slots for each. Each space's answer sets must number exactly its count, at both bounds. A wrong space passes only if the count makes the same mistake in different code.
- **The bounds.** A bound is a set of the program's constants (`SPACES` in `tests/spaces.py`). The *PR bound* runs in README § Verify, and the *slow bound* under `uv run pytest -m slow`. Each is measured, not guessed (`correctness-strategy.md` §9 #10): the PR bounds keep README § Verify under two minutes on ten cores, and the slow bounds finish in about a quarter of an hour. A leaf compares an operand with `1` by `eq` or `neq`, and by `lt` or `gteq` too where `operators` is 4. In `rules.lp`, `operands` 1 gives the leaves one operand instead of two. In `candidates.lp`, `actions` 1 gives the rules and the request the action `use` only. In a duty space, `subjects` 1 makes the request's subject `ex:alice`, and 2 `ex:alice` or none; `actors` 1 means no evidence, and 3 no evidence or evidence by `ex:alice` or `ex:bob`.

  | Space | Program | What it varies | PR bound | Inputs | Slow bound | Inputs |
  |---|---|---|---|---|---|---|
  | `leaves` | `rules.lp` | up to two rules, each with at most one leaf, under every operand status | `operators` 2, `operands` 1 | 180 | `operators` 4 | 3,510 |
  | `trees` | `rules.lp` | one rule with a tree, under every operand status | `size` 3, `operators` 2, `operands` 1 | 112 | `size` 4, `operators` 4 | 14,420 |
  | `pinned` | `rules.lp` | one rule with a larger tree; operand 0 `value` and operand 1 `unresolved`, so a leaf is `t`, `f`, or paired `u` | `size` 4, `operators` 2 | 322 | `size` 6, `operators` 2 | 8,186 |
  | `candidates` | `candidates.lp` | unconstrained rules over two actions, two targets, and three assignees, and the request | `rules` 1 | 192 | `rules` 2 | 4,896 |
  | `conflicts` | `candidates.lp` | the same over one action, so that three rules stay cheap | `rules` 1, `actions` 1 | 48 | `rules` 3, `actions` 1 | 4,120 |
  | `xone` | `xone.lp` | the coverage targets below | `largest` 7 | 4,176 | `largest` 8 | 28,080 |
  | `routes` | `duties.lp` | up to two permissions with unguarded duties, each with or without evidence and a passed deadline, and the subject `ex:alice` or none | `duties` 2 | 472 | `duties` 3 | 3,608 |

- **The differential** (`test_pr_space_matches_brute_force`, `test_slow_space_matches_brute_force`). Every input of every space must give the oracle's reply. Each space is cut into *shards*, every `of`-th input from the `k`-th, at most 300 inputs each at the PR bound and 3,000 at the slow bound, and each shard is a test of its own, so that pytest-xdist spreads them over the workers.
- **Two coverage targets** (`xone.lp`). An `xone` passes liveness to its members term by term (`explain.lp`, `live/4`), and each of its two checks needs a tree past the `trees` and `pinned` bounds:
  - A positive `xone` passes liveness through a term only when no other member of the term is `f` there. To test that, a `u` leaf must lie in an `xone` with two `t` members, so that every term has an `f` conjunct, and one of the two must be compound, because with operand 0 `value`, operand 1 `unresolved`, and `eq` and `neq`, the only `t` leaf is `l(0,eq)`, and two equal leaf members are malformed.
  - A negated `xone` passes liveness to the members of one term only when no other negated term is `f`. To test that, a `u` leaf must lie in a compound term of a negated `xone` beside a term that is `t`.

  Either way the rule's atom must not be `f`, since an `f` atom reports no unknown parts, so the `xone` needs a sibling that keeps the tree from being `f`. The smallest such trees are `or(xone(t, or(t, u)), t)`, with seven nodes and leaves, and `or(not(xone(t, and(f, u))), t)`, with eight. There are 126,562 trees up to size 8 over two operands with `eq` and `neq` (`catalog(2, 2, 8)`); each as one permission and as one prohibition, at about 35 ms a check, is 2 × 126,562 × 0.035 s ≈ 2.5 CPU-hours. So `xone.lp` fixes the forms `node(F, node(xone, A, B), C)` and `node(F, neg(node(xone, A, B)), C)`, and enumerates their holes from the catalog, with `A` and `B` different and at least one of them compound. The smallest-first order gives the smallest witness that `decisions/0009` #6(c) asks of `#minimize`, and checks every other input on the way.
- **Worked example** (`test_negated_xone_worked_example`). Input 8,180 of `xone` at its slow bound is the answer set

  ```text
  slot(1,r(prohibition,node(or,neg(node(xone,l(0,eq),node(and,l(0,neq),l(1,eq)))),l(0,eq))))
  operand(0,value) operand(1,unresolved) conflict(perm)
  ```

  Operand 0 has the value `1`, so `l(0,eq)` is `t` and `l(0,neq)` is `f`; operand 1 is unresolved, so `l(1,eq)` is `u`. `tests/spaces.py` maps it to the prohibition `r0` on `use` of target `a` with the constraint `or(not(xone(t, and(f, u))), t)`. The `and` is `f` whatever `u` is, the `xone` has exactly one `t` member and is `t`, its negation is `f`, and the `or` is `t`: the oracle replies `Deny`, with `r0` as the basis and no unknown parts. The program agrees by `live/4`. The `or` is read `pos` and passes liveness to both members; `dprod:not` flips it to `neg`; under `neg`, the `xone` passes liveness to its term `and(f, u)` only if the other negated term is not `f`, and that term is the negation of the `t` leaf, so it is `f`. No leaf below the `and` is live, and `ex:o1` is not named. The mutant `live-negated-xone-ignores-terms` drops that check: under `neg`, the `and` is a disjunction of its members read negated, so its `f` member does not stop liveness, and the mutant replies the same `Deny` but names `ex:o1` as `unresolved`. This is the first input of the space that exposes the mutant, and generation alone does not reach it in 2,000 draws.
- **Shapes** (`test_slow_spaces_reach_each_shape`, slow). The slow spaces together must reach every shape that the two shape tests require of the generators. The PR spaces miss two (a `u` leaf that only `f` atoms read, and an `Indeterminate` with a non-pivotal `u` atom), so the test runs only at the slow bounds.
- **Exposing the mutants** (`test_spaces_alone_expose_mutant`, slow; `test_each_mutant_has_a_space`). Each mutant must fail on some input of the space and bound that `EXPOSED_BY` names for it, with no explicit case and no generated draw. Without this, a lowered bound or a tightened symmetry constraint that stopped reaching a mutant's shape would pass every other test.
- **Cost.** On a 10-core arm64 Mac, the PR suite takes 113 s, of which the spaces are about 430 of 900 CPU-seconds. The slow suite checks 73,012 inputs in about 14 minutes and 5,600 CPU-seconds, about 76 ms an input with every core busy. Its longest test is `test_spaces_alone_expose_mutant` for `live-negated-xone-ignores-terms`, which checks inputs 0 to 8,180 of `xone` one after another, in about six minutes.

## Claims M and W

Two claims of `correctness-strategy.md` §4.8 are checked over the spaces.

- **Claim M, monotonicity** (`test_space_is_monotone`, `test_monotone_check_kills_mutant`). W2 and W3 will compute a verdict's range as *Computing it* in `due2-workflows.md` §6.4 does. A completion variable is *uniform* when every occurrence of it moves the verdict the same way as it becomes true, and *mixed* otherwise. Mixed variables are enumerated, and uniform ones completed at the most restrictive and the most permissive extreme. That is right only if the verdict is monotone in every finding. clingo-i and the oracle both enumerate every completion, so neither depends on it, and the differentials cannot see it fail. This test computes the range both ways on the oracle's semantics, without clingo (`monotone_ranges`), for every input of every space, and the two must be equal. `directions` gives each variable one direction per occurrence, so a variable with both is mixed. `occurrences` keeps a leaf's sign through `and` and `or`, flips it under `dprod:not` and for a complement operator, and gives an `xone` member both signs, because an `xone` is not monotone in its members. The item turns the sign into a direction: up for a permission and a `fulfilled`, down for a prohibition and an `owed`; an obligation's `in_force` moves the verdict neither way (`decisions/0045`). An atom left `u` by an opaque part moves with its `fin` variable. The differential checks that clingo-i's `verdict_range` equals the oracle's on the same inputs, so on these inputs the property holds for clingo-i too. All 73,012 slow inputs pass; 25,022 of them have a mixed variable, and 11,210 of those have a definite verdict. Two mutants of the computation show that the check can fail:
  - `prohibitions-cancel`: a second prohibition that applies lifts a `Deny` to `NotApplicable`; exposed by `leaves` at the PR bound.
  - `mixed-as-uniform`: each mixed variable completed as if uniform; exposed by `trees` at the slow bound only, because at the PR bounds the extremes always give the same range as enumerating.
- **Claim W, the basis waiver** (`check_waiver`, `test_pr_spaces_hold_by_cases`, `test_waiver_worked_example`, `test_waiver_check_kills_missing_paired`). `tools/check_corpus.py` lets a definite `Permit` or `Deny` lack the atoms that determine it only when the scenario lists an `unresolved` unknown part. Such a verdict *holds by cases*: no atom plays the role in every completion. `resolve.lp`, *The cautious basis*, argues that the waiver is sound, because holding by cases needs a `u` finding that reads a paired leaf. `check` and `check_duties` check the claim on every reply, generated or from a space: when `holds_by_cases` finds the shape, reading the basis as the corpus checker does, the reply must list an `unresolved` unknown part. `Pending` is outside the claim: dominance is not monotone, so a `Pending` under unknowns can lack either role whatever the status of its unknown parts (`resolve.lp`, *The cautious basis*). The corpus checker checks only its roles' kinds, and `holds_by_cases` is false for it.

  The PR spaces reach the shape in two inputs of `leaves`, and `test_pr_spaces_hold_by_cases` fails if a change to the spaces loses them. Among duties the shape needs the slow bound, where the spaces reach it in 61 inputs: 20 of `leaves` and 41 of `guards`. Input 450 of `guards` (`test_waiver_worked_example`) has two permissions for `use` on `a`: `r0`, which requires the duty `d0`, and `r1`, whose constraint is the leaf `o0 eq`. `d0` is guarded by the same leaf `o0 eq`, its deadline has passed with no evidence, and `o0` is unresolved. If `o0 eq` holds, `d0` is owed and violated, so `r0` is closed and `r1` permits; otherwise `r1` does not apply, `d0` is not owed, and `r0` permits. The verdict is `Permit` in every completion, but neither permission permits in all of them, so the basis is empty, and the unknown parts name `o0` as `unresolved` under `d0` and `r1`. The mutant `missing-paired` shares one variable between two leaves on one missing operand, which breaks the premise that only `unresolved` parts are shared: a verdict then holds by cases with only `missing` unknown parts, and `check_waiver` fails on an input of `leaves` without the oracle.

## The driver

`test_flatten.py`, over the repo's own files.

- **Graph round trip.** The flatten must drop nothing. For every policy and module file, `triple/3` decoded back to RDF is isomorphic to the parsed graph, lexical forms included. A plain literal and its `xsd:string` twin are one term (RDF 1.1).
- **Input round trip.** For every corpus vector, the request and SOTW facts decode back to the input, with names expanded and lists read as sets.
- **Invariance** (Hypothesis). The facts must not depend on serialisation order. Shuffling the triples and relabelling the blank nodes of a policy, written as N-Triples, gives the same fact set. So does shuffling the keys and lists of a vector's input, and the reply is the same.
- **Acceptance.** Over the corpus policies, the vendored DPROD examples, the shipped modules, and the external suites:
  - the driver parses exactly the files that `tools/check_corpus.py` and `tools/check_odrl22.py` parse. All three use rdflib's default parse, register #3's common mode, so this is checked rather than assumed;
  - every file that parses, the driver flattens and places without error, a superset of what either checker accepts, so the SHACL run is not needed here;
  - no file `check_corpus.py` admits holds an unplaceable literal, so the driver can place every value due2 admits.
- **Errors.** An unknown field, a missing required field, a duplicate evidence id, a bare-string value, a second answer from one source, and an answer in a list without a `source` are each an error.

## The values

`test_values.py`.

- **Order** (Hypothesis). A position must order exactly as its value. Over generated decimals in any lexical form, and instants in any timezone with any number of fractional digits, positions order exactly as the values do. Day-time durations take their value from `timedelta`. The oracles are Python's `Decimal`, `datetime`, and `timedelta`, which share no code with `values.py`.
- **Pass-through.** 32-bit integers keep their value as their position. One wider integer or one decimal turns the space into ranks.
- **Sums.** The XSD 1.1 Part 2 Appendix E example (`2000-01-12T12:13:14Z` + `P1Y3M5DT7H10M3.3S` = `2001-04-17T19:23:17.3Z`), end-of-month clamping, a timezone near a month's end, and, by Hypothesis, day-time sums against `datetime + timedelta`.
- **Placement.** Each unplaceable reason, and lexical forms at the edges of their spaces: `24:00:00`, year zero and negative years, leap days, and the ranges of the derived integer types.

## The documentation

`test_docs.py` (`ways-of-working.md` §15.10). The generated reference is only as complete as its doc blocks:

- every relation the program defines has exactly one `%*!` doc block, in the file that defines it;
- each block's first sentence is whole, because clindocs' predicate table cuts a block at its first full stop;
- each file header's **Consumes** and **Provides** lists match its rules, read with `clingo.ast`;
- every input fact the program reads is named in the `clingo_i/flatten.py` docstring;
- `docs/program.lp` includes the program files in the interpreter's order;
- no section reference in the spike is bare.
