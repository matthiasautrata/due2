# due2 — Annotated references

**Status:** living list, started 2026-10-17.

Every source that informed a decision, a spec section, or a review goes here, with what was looked at, why, and what we took from it. The list is the seed of a future paper's bibliography and related-work section. It is also the knowledge base: a newcomer can see from it which established notions due2 builds on, and where.

**Entry format.** Citation and link · **Read:** when, for which issue, and how much (abstract, sections, code at a commit) · **Learned:** what we took or rejected, in one to three sentences · **Used in:** the sections that cite it. Add an entry when research informs work, and update **Used in** when a citation moves. Tooling and benchmark sources for the host question stay in the archived `implementation-alternatives-ii.md` § References. Unfinished citations are marked *(complete for the .bib)*.

## 1. ODRL: standards, semantics, evaluators

- **W3C, *ODRL Information Model 2.2* and *ODRL Vocabulary & Expression 2.2*** (2018). <https://www.w3.org/TR/odrl-model/>, <https://www.w3.org/TR/odrl-vocab/>.
  **Read:** throughout. **Learned:** the normative base: rule structure, conflict strategies, the set-based operators (Vocab §3.16.7–3.16.12) and their list right operands. A set right operand may also be written as repeated values: IM §2.5.1 asks for a "list" without naming `rdf:List`, Vocab §5.1 says only that `rdf:List` SHOULD be used, the vocabulary file (`ODRL22.ttl`) gives `odrl:rightOperand` no functional restriction and notes that "a list of values may be used", and the normative JSON-LD context (<http://www.w3.org/ns/odrl.jsonld>) maps `rightOperand` without `@container: @list`, so a JSON array in ODRL's own serialisation becomes repeated triples. None of the IM, the Vocabulary, or `ODRL22.ttl` mentions an empty list or an empty set as a right operand. IM §2.5.2 gives a logical constraint's operand "a list of the existing Constraint instances", and nothing gives an empty one a meaning; its validation requirements add that "All of the operand values MUST be unique Constraint instances", which forbids a list that names one node twice but not two nodes that state the same constraint, and the Vocabulary's `odrl:xone`, "satisfied when only one, and not more, of the Constraints is satisfied", does not say which it counts. IM §2.3 has every member of a `PartyCollection` "undertake the same functional role in the Rule", and IM §2.6.3 obliges the party that performs a duty to satisfy it, so each member bears a duty whose bearer is a collection. **Used in:** `odrl22-shape.ttl`, `odrl22-conformance.md`, normalisation spec, `decisions/0005`, `decisions/0013` and its amendment, `decisions/0017`, `decisions/0018`, `decisions/0022`.
- **Steyskal and Polleres, *Towards Formal Semantics for ODRL Policies*,** RuleML 2015. <https://aic.ai.wu.ac.at/~polleres/publications/stey-poll-2015RuleML.pdf>.
  **Read:** for normalisation stage 1. **Learned:** the first formal reading of ODRL's compound forms. **Used in:** normalisation spec § References.
- **De Vos, Kirrane, Padget, and Satoh, *ODRL Policy Modelling and Compliance Checking*,** RuleML+RR 2019. <https://doi.org/10.1007/978-3-030-31095-0_3>.
  **Read:** for normalisation stage 1; again 2026-10-18, §§1–4. **Learned:** compliance checking of ODRL in answer set programming, a precedent for `decisions/0009`. An ODRL profile (ORCP) for business policies and regulatory norms is translated to InstAL, an institutional-action language that compiles to ASP and runs on clingo under closed-world reasoning, so what is not derived is false; `isA` is implemented as equality. We found no journal version (searched 2026-10-18 for a TPLP paper). **Used in:** normalisation spec § References.
- **Salas, Pareti, Yumuşak, Gheisari, Ibáñez, and Konstantinidis, *Evaluation and Comparison Semantics for ODRL*,** 2025. arXiv:2509.05139.
  **Read:** 2026-10-09 and again 2026-10-17 (#55). **Learned:** monitoring as the modality; null is false (SPARQL filter semantics); hierarchy reasoning kept out of the core and materialised; duties as relations over rules; duty preconditions temporal over the event log, which made approval a fact in due2. Their reading of the set operators differs from earlier work (`decisions/0005`). **Used in:** `due2-architecture.md` §8.1, `decisions/0005`, normalisation spec § References.
- **Salas, Pareti, and Konstantinidis, *ODRL Policy Comparison Through Normalisation*,** 2026. arXiv:2603.12926.
  **Read:** 2026-10-17 (#55). **Learned:** a constraint normal form (DNF, operators regularised, disjoint intervals) that makes containment set membership. It composes with due2's structural stage 1, but excludes the set operators due2 admits. **Used in:** `due2-architecture.md` §8.1; candidate input to #15.
- **Salas et al., *A Formally Grounded ODRL Evaluator: Implementation and Comparison*,** 2026. arXiv:2607.15987.
  **Read:** 2026-10-17 (#55), Defs 1, 3, 5 and Thm 4.1. **Learned:** access control as validity of ω ∪ {e_R}, which coincides with streaming monitoring for permissions, prohibitions and duties. Their Defs 1 and 3 are a candidate for due2's monitoring question (#6), with `U` in place of false. **Used in:** `due2-architecture.md` §8.1.
- **Bonatti, Fornara, and Harth,** OPAL@ESWC 2025, CEUR 3977, Table 1 *(complete for the .bib)*.
  **Read:** for `decisions/0005`. **Learned:** a two-valued membership reading of `isPartOf`, `hasPart` and `isA`. **Used in:** `decisions/0005`.
- **Mustafa, Collarana, Peng, Haque, Lange-Bever, Quix, and Decker, *Denotational Semantics for ODRL: Knowledge-Based Constraint Conflict Detection*,** 2026. arXiv:2602.19883. The benchmark: <https://github.com/Daham-Mustaf/odrl-benchmark> (problems CC BY 4.0, generators Apache-2.0).
  **Read:** for `decisions/0005`; again 2026-10-18, in full (Defs 2, 3, 6, 11; Remarks 1–3; Tables 2, 5, 6), and the benchmark at `8795b74` (as data, not run). **Learned:** a Kleene reading of the set operators by downward and upward closure, the reading closest to due2's. Its verdict is about a pair of constraints (`Conflict`, `Compatible` or `Unknown`), not a request: a right-operand value with no concept in the knowledge base (KB) gives `Unknown`, and so does `xone` when the KB's disjointness axioms do not rule out the other branches (Table 6). The KB is open-world in its value mapping and its disjointness, and fixed in its concepts and their order (Prop 3). Remark 1 rejects supervaluation, which due2-workflows.md §6.4's completion resembles, because it quantifies over completions and leaves the EPR fragment; due2 completes over finitely many literals instead. At request time (Def 11) the reading is two-valued: a request value with no KB concept fails the constraint, and a constraint whose value has no concept is satisfied, where due2 gives `U` to both; a request value in the KB but outside the denotation fails, as in `decisions/0015` #4. The benchmark holds 389 TPTP problems (and 390 SMT-LIB encodings) in three families (54 knowledge-graph constraints, 263 axis decomposition, 72 temporal decomposition); the paper reports 154 for its family, which we have not reconciled with the 54. All are constraint-pair problems except ten `Runtime` problems, which check one request value against one constraint on the authors' axis operands. **Used in:** `decisions/0005`.
- **Havur, Steyskal, Panasiuk, Fensel, Mireles, Pellegrini, Thurner, Polleres, and Kirrane, *Automatic License Compatibility Checking*,** SEMANTiCS 2019 Posters and Demos, CEUR 2451, paper 13. <https://ceur-ws.org/Vol-2451/paper-13.pdf>. Code and license library (DALICC): <https://gitlab.com/coypu-project/dalicc>, a fork of the original. The code is MIT; 344 of the 347 license files state CC BY 4.0 in their header, and the other three (EtaLab2, DLDEBY20, Weltrisikobericht) state no license.
  **Read:** 2026-10-18, the paper in full (four pages), and the reasoner and license data at `6c68f58` (as data, not run). **Learned:** licenses written in ODRL 2.2, with a dependency graph between actions (`odrl:includedIn`, `odrl:implies`, `owl:sameAs`, `dalicc:contradicts`). Compatibility is checked by two HEX programs of 70 lines, run with hexlite over clingo: a conflict is a permission and a prohibition on the same action, or on actions the graph relates. The check is two-valued and needs no request. The repository has no tests or expected results, and the paper reports no evaluation. The graph contradicts the library: it puts `odrl:display` and `odrl:present` under `dalicc:promote`, and 329 licenses permit display and present while prohibiting promote. The conflict rule in `reasoner/app/programs/query.lp` does not require the two licenses to differ, so it reports each of them as conflicting with itself. Under due2, a request to display such a work, with the graph's `includedIn` edges loaded, matches the permission and the prohibition; the licenses state no `odrl:conflict`, so `invalid` voids the policy (`due2-workflows.md` §6.2). Of the library's 347 licenses, 346 pass both `check_corpus.py` and `check_odrl22.py`; the other uses free-text left operands, with `and` and `or` as operators. Only that one has a constraint, and 342 carry duties. They passed because both checkers missed two things. Every license uses `dalicc:` actions and declares no `odrl:profile`, which IM §2.1 forbids; both checkers checked that rule only for the DPROD and due2 namespaces, and since `decisions/0020` (#78) all 347 fail it. And every license's target is a blank-node `odrl:AssetCollection` described only by `dct:type` (software, dataset, creative work), with no assignee. Stage 1 gives such a node a generated identity (`odrl-compound-to-atomic-normalization.md` §5.1), so no request or closure edge can name it. Under due2 a request that names a target is `NotApplicable` against these licenses, and one that names none can be `Indeterminate`; W1 warns with `AnonymousEntity` (`odrl-compound-to-atomic-normalization.md` §3, #79), and `due2-anonymous-target` is the case. A license meant as an offer to any work released under it needs a named collection with membership edges, or a collection refinement, which due2 rejects (#21). Overall, of little value to due2. The paper is a four-page demo with no evaluation, the reasoner is 70 lines with no tests, and the license library is contradicted by the project's own dependency graph. Nothing is vendored or translated into the corpus. The checks above were worth running for what they showed about due2's own checkers. **Used in:** #78, #79, `due2-anonymous-target`.

## 2. Explaining a decision: causality, formal XAI, provenance

Surveyed 2026-10-17 for #59 (the `unknown` role and `verdict_range`), #58 (a witness for `Indeterminate`), #60, and #61 (remedies). The outcome is `decisions/0011`.

- **Halpern and Pearl, *Causes and Explanations: A Structural-Model Approach. Part I: Causes*,** British Journal for the Philosophy of Science 56, 2005. **Halpern, *A Modification of the Halpern–Pearl Definition of Causality*,** IJCAI 2015 (<https://www.cs.cornell.edu/home/halpern/papers/newcause.pdf>). **Halpern, *Actual Causality*,** MIT Press 2016.
  **Read:** 2026-10-17, definitions and survey material, not the full book. **Learned:** actual causation is counterfactual dependence under a contingency. A due2 variable that, flipped alone, changes some completion's verdict is a cause in this sense under the contingency that fixes the others. due2 has no actual world, only completions, so we use dependence over all of them. **Used in:** `decisions/0011`, `due2-workflows.md` §6.4.
- **Chockler and Halpern, *Responsibility and Blame: A Structural-Model Approach*,** JAIR 22, 2004.
  **Read:** 2026-10-17, the definition. **Learned:** degree of responsibility 1/(k+1), with k the fewest changes that make the outcome counterfactually depend on the variable. due2 reports membership (responsibility > 0), not degree. **Used in:** `decisions/0011` (Rejected: scores).
- **Aleksandrowicz, Chockler, Halpern, and Ivrii, *The Computational Complexity of Structure-Based Causality*,** JAIR 2017 (AAAI 2014). arXiv:1412.3076.
  **Read:** 2026-10-17, abstract. **Learned:** deciding actual causation is NP-complete in binary models under the modified definition, which is why W3 bounds the computation as it bounds the frontier. **Used in:** `decisions/0011`.
- **O'Donnell, *Analysis of Boolean Functions*,** Cambridge University Press 2014.
  **Learned:** the influence of variable i on f is the probability that flipping i changes f; it is non-zero iff i is relevant (essential). The pivotal literals of due2 are the relevant variables of the verdict function restricted to the completions; Banzhaf power is the same influence. **Used in:** `decisions/0011`.
- **Marques-Silva, *Logic-Based Explainability in Machine Learning*,** Reasoning Web 2022. arXiv:2211.00541.
  **Read:** 2026-10-17, the definitions. **Learned:** abductive explanations (AXp: subset-minimal sufficient reasons, prime implicants) and contrastive explanations (CXp: minimal changes that switch the outcome), dual by minimal hitting sets (Ignatiev, Narodytska, Asher, and Marques-Silva, *From Contrastive to Abductive Explanations and Back Again*, AI*IA 2020). A literal is relevant iff it is in some AXp. The Pending frontier is already an abductive answer; remedies (#61) would be the AXp and CXp of the other verdicts. **Used in:** `decisions/0011`, #61.
- **Izza, Ignatiev, Stuckey, and Marques-Silva, *Delivering Inflated Explanations*,** AAAI 2024. arXiv:2306.15272.
  **Read:** 2026-10-17, abstract. **Learned:** an explanation may give each feature a set of values that keep the decision, not one value. That is the shape a remedy over an enumerated or ranged fact would take, and it relates to domain-aware completion (#25). **Used in:** #61.
- **Buneman, Khanna, and Tan, *Why and Where: A Characterization of Data Provenance*,** ICDT 2001. **Green, Karvounarakis, and Tannen, *Provenance Semirings*,** PODS 2007 (<https://www.cs.ucdavis.edu/~green/papers/pods07.pdf>).
  **Read:** 2026-10-17, framework only. **Learned:** why-provenance (minimal witnesses) and its generalisation to semiring annotations, with Datalog as a fixed point. due2's `basis` is why-provenance of a finding. We do not adopt the polynomial machinery: the trace records the determining parts, not every derivation. **Used in:** `decisions/0011` (Context).
- **Chapman and Jagadish, *Why Not?*,** SIGMOD 2009.
  **Learned:** why-not provenance: why an expected answer is missing. due2's `eliminated` answers why-not for a candidate removed by conflict, and remedies (#61) generalise it. **Used in:** #61.
- **Imieliński and Lipski, *Incomplete Information in Relational Databases*,** JACM 1984. **Libkin, *How to Define Certain Answers*,** IJCAI 2015.
  **Read:** 2026-10-17, abstract. **Learned:** certain answers, those true in every completion of an incomplete database, are what due2's definite verdict is (invariance over completions, `due2-workflows.md` §6.4). Libkin's critique of one-size-fits-all certain answers is worth reading before domain-aware completion (#25). **Used in:** `decisions/0011` (Context).
- **Cabalar, Fandinno, and Fink, *Causal Graph Justifications of Logic Programs*,** TPLP 2014. arXiv:1409.7281. **Cabalar, Fandinno, and Muñiz, *A System for Explainable Answer Set Programming* (xclingo),** ICLP 2020. arXiv:2009.10242.
  **Read:** 2026-10-17, abstracts. **Learned:** justifications of an atom in an answer set as causal terms (product for joint, sum for alternative causes), and xclingo, which builds derivation trees from comment annotations. Not adopted as a dependency: due2's trace is already the derivation (`decisions/0010`). A candidate for rendering clingo-i's derivations later. **Used in:** `decisions/0011` (Rejected).
- ***An XAI View on Explainable ASP: Methods, Systems, and Perspectives*,** 2026. arXiv:2601.14764 *(complete for the .bib)*.
  **Read:** 2026-10-17, abstract only. **Learned:** a survey of ASP explanation methods against XAI user needs; read in full before #47. **Used in:** —.

## 3. Policy engines: what they report

- **OASIS, *eXtensible Access Control Markup Language (XACML) 3.0*,** 2013.
  **Read:** 2026-10-17, the extended Indeterminate and missing-attribute status. **Learned:** `Indeterminate{P}`, `{D}`, `{DP}` record which decisions an indeterminate rule could have produced, because a rule that might match cannot override, but makes the result uncertain. The same reasoning is behind due2's "`U` atoms eliminate nothing" (`due2-workflows.md` §6.2) and `verdict_range`. The PDP may name the missing attribute, which is the `unknown` role. **Used in:** `decisions/0011`.
- **Cutler et al., *Cedar: A New Language for Expressive, Fast, Safe, and Analyzable Authorization*,** OOPSLA 2024. Docs: <https://docs.cedarpolicy.com/auth/authorization.html>; partial evaluation in the `cedar-policy` crate (`PartialResponse`).
  **Read:** 2026-10-17, the authorization docs. **Learned:** the response is the decision plus its *determining policies*: the satisfied permits for Allow, the satisfied forbids for Deny, empty for a default Deny. That is due2's `verdict_basis` for `Permit` and `Deny`, and the empty basis of `NotApplicable`. Partial evaluation returns residual policies over unknowns, the analogue of a remedy. **Used in:** `decisions/0011`, #61.

## 6. Vocabularies and datatypes

- **W3C, *SKOS Simple Knowledge Organization System Reference*** (Miles and Bechhofer, eds.), 2009. <https://www.w3.org/TR/skos-reference/>.
  **Read:** 2026-10-17, for #52: §1.3, §4 (schemes, with Example 9 in §4.6), §8 (semantic relations), and the integrity and entailment conditions S7, S8, S22, S24, S25. **Learned:** concepts are individuals, related "never as class or property axioms" (§1.3); `skos:broader` is not transitive but is a sub-property of the transitive `skos:broaderTransitive` (S22, S24; §8.6.6), and `skos:narrower` is its inverse (S25); `skos:topConceptOf` is a sub-property of `skos:inScheme` and the inverse of `skos:hasTopConcept` (S7, S8); scheme membership is not inherited along the hierarchy (§4.6). **Used in:** `decisions/0015`, `due2-profiles.md` §4, §6, `due2-workflows.md` §3.1.

The next five are the sources of the testing statistics in the 2026-10-21 briefing (`docs/briefings/due2-briefing-2026-10-21.md` §5). Each was cited from the standard account of its result, not read in the original; read the originals before a paper cites them.

- **H. D. Mills, *On the Statistical Validation of Computer Programs*,** IBM Federal Systems Division, report FSC-72-6015, 1972. *(complete for the .bib)*
  **Read:** 2026-10-21, for the briefing; not read in the original. **Learned:** error seeding: plant S faults, test, and if s planted and n real faults are found, estimate the real total as n·S/s, assuming planted faults are as hard to find as real ones. If all S planted faults are found and the number n of real faults found is at most K, the confidence that the program had at most K real faults is S/(S+K+1). **Used in:** `due2-briefing-2026-10-21.md` §5.3, and §5.4 of the same file, on why due2's 22 mutants support no such estimate.
- **G. J. Myers, *The Art of Software Testing*,** Wiley, 1979. *(complete for the .bib)*
  **Read:** 2026-10-21, for the briefing; not read in the original. **Learned:** nothing beyond the Mills entry above; it is the textbook that made Mills' seeding model and confidence formula widely known, and a reader without access to the IBM report can check the formula there. **Used in:** `due2-briefing-2026-10-21.md` §5.3.
- **R. A. DeMillo, R. J. Lipton, F. G. Sayward, *Hints on Test Data Selection: Help for the Practicing Programmer*,** IEEE Computer 11(4), 1978. DOI 10.1109/C-M.1978.218136.
  **Read:** 2026-10-21, for the briefing; not read in the original. **Learned:** mutation testing: a test set that distinguishes a program from its simple mutants is adequate for faults of that kind, and the coupling effect, that tests catching simple faults catch most complex ones. **Used in:** `due2-briefing-2026-10-21.md` §5.5; the mutant tests of `spikes/clingo-i/tests/test_brute_force.py` (#47, #49), and the test that the bounded-exhaustive spaces of `spikes/clingo-i/tests/test_spaces.py` expose every mutant (#44).
- **R. Just, D. Jalali, L. Inozemtseva, M. D. Ernst, R. Holmes, G. Fraser, *Are Mutants a Valid Substitute for Real Faults in Software Testing?*,** FSE 2014. DOI 10.1145/2635868.2635929.
  **Read:** 2026-10-21, for the briefing; the abstract's result, not the paper. **Learned:** on real faults from open-source Java projects, mutant detection correlates with real-fault detection, but a share of real faults couple to no common mutant. So killing every mutant is evidence about faults like the mutants, not about all faults. **Used in:** `due2-briefing-2026-10-21.md` §5.5.
- **J. A. Hanley, A. Lippman-Hand, *If Nothing Goes Wrong, Is Everything All Right? Interpreting Zero Numerators*,** JAMA 249(13), 1983. DOI 10.1001/jama.1983.03330370053031.
  **Read:** 2026-10-21, for the briefing; not read in the original. **Learned:** the rule of three: after n independent trials with no event, the one-sided 95% upper bound on the event's rate is about 3/n, since (1 − p)ⁿ = 0.05 gives p ≈ −ln 0.05 / n ≈ 3/n. **Used in:** `due2-briefing-2026-10-21.md` §5.2 and §5.5, for the zero-failure runs and the two mutants no generated draw exposes.

## 8. Architecture and migration

The sources of the component structure and the migration plan in `due2-platform.md`. Each is a practitioner's essay or a tool, not a paper.

- **A. Cockburn, *Hexagonal Architecture* (ports and adapters),** 2005. <https://alistair.cockburn.us/hexagonal-architecture/> *(complete for the .bib)*
  **Read:** 2026-10-21, for the platform design; the essay. **Learned:** an application exposes ports, interfaces stated in its own terms, and each outside technology (a user interface, a test harness, a database, another service) connects through an adapter for one port. The application can then be driven by tests and by people alike, and a technology is swapped by writing an adapter, not by changing the application. **Used in:** `due2-platform.md` §1.2, the port and adapter vocabulary and one schema behind REST and MCP.
- **M. Fowler, *Strangler Fig Application*,** martinfowler.com, 2004, revised 2024. <https://martinfowler.com/bliki/StranglerFigApplication.html>
  **Read:** 2026-10-21, for the platform design; the article. **Learned:** replace a legacy system gradually: build the new system around the edges of the old one, move one piece of behaviour at a time, and let the old one shrink until it can be removed. Each step delivers value and can be stopped, against the high risk of a big-bang rewrite. Interception points, where calls can be routed to either system, are what make it possible. **Used in:** `due2-platform.md` §4.
- **M. Fowler, *Branch By Abstraction*,** martinfowler.com, 2014. <https://martinfowler.com/bliki/BranchByAbstraction.html> The technique is credited there to Stacy Curl and Paul Hammant.
  **Read:** 2026-10-21, for the platform design; the article. **Learned:** to replace a component that many callers use, put an abstraction in front of it, move the callers onto the abstraction, build the new implementation behind it, and switch over, possibly per caller, with the system releasable at every step. **Used in:** `due2-platform.md` §4, the choice of engine behind each route.
- **GitHub, *Scientist*,** a Ruby library for refactoring critical paths, 2016. <https://github.com/github/scientist>; J. Toth, *Scientist: Measure Twice, Cut Over Once*, GitHub blog, 2016. *(complete for the .bib)*
  **Read:** 2026-10-21, for the platform design; the README and the blog post. **Learned:** an experiment runs the old code path (the control) and the new one (the candidate) on the same input, always returns the control's result, and records every mismatch with its input and timings. Exceptions in the candidate are recorded, not raised. The candidate may not have side effects, which is why it suits a pure function. **Used in:** `due2-platform.md` §4, the shadow phase.
